# A working copy's counts of Errors and Warnings are kept with the revisions they were worked out against

A person's list of working copies takes each copy's counts of Errors and Warnings from a table that keeps them, beside the two revisions they were worked out against: the catalog's and the library's. A working copy whose kept counts name the revision it is at and the revision the library is at is listed from them. One that has no kept counts, or whose kept counts name another revision, is read whole and validated, as every working copy in the list is today, and what that finds is kept for the next ask. The list keeps the counts, and nothing else writes them.

This is the decision alone, and it waits for the maintainer's yes. Nothing of it is built before that.

Where the time of the list goes was known before any trace was read. The code marks the place as a shortcut, taken on purpose: "each working copy is read whole and validated, ten queries apiece for the 20 an owner can have at most. Keep the counts with the catalog if this list gets slow" (`CatalogController.java`). On 2026-10-14 the list of twenty working copies of Sedan 2027, the largest catalog the demo starts with, took the API a median of 416 ms on the host, where the ticket's bar is a quarter of a second. The trace of the median ask confirmed the place and measured it: of the request's 417.6 ms, the twenty readings of a catalog took 196.6 together, the twenty readings of what validation needs of the library 152.7, the twenty workings-out of the issues 15.8, and the gaps between one copy's steps and the next's, where one transaction ends and the next begins, 23.2. That is 388 ms of the 417.6 that go with the twenty reads, and about 27 ms that the request does once, before its first step and after its last. [The measurements](../working-copy-list-measurements.md) have the run, the trace as a table, and the chart.

## What is kept, and who keeps it

- **One table, added by one migration that changes nothing else.** A row for a working copy: the catalog's id, which refers to `catalog` with `ON DELETE CASCADE` as `submission_summary`'s does, the catalog's revision, the library's revision, the count of Errors, the count of Warnings, and when they were kept. The image released before the migration, and a reverted one, run on the database it leaves, since nothing of theirs reads or writes the table and the rows go with their catalog.
- **The list keeps a count, when it has read a working copy whole.** Reading a catalog is one transaction that gives every statement in it one view of the database, so the contents, what validation needs of the library, and the catalog's revision are of one moment. The library's revision is read in that same transaction, which is the one change to the read, and so names the library the issues were worked out against. The row is written after the transaction, with one statement that inserts the row or replaces it, and replaces it only when neither revision it holds is newer than the one coming in, as `approved_check` is replaced only by a check against a library revision at least as new. So of two asks of the same list at once, the one that read the older view never writes over the newer row.
- **Nothing else writes the table.** Not the answer to an edit, though it validates the whole catalog and has the counts in hand, not a submission, not a job. One writer, in one place, which is the one reader.
- **The list's own statement reads the kept counts beside the working copies,** with the library's revision, and lists from the row every copy whose row names both revisions. The others it reads whole, in the order it lists them, and keeps. Whether a copy is stale is not kept: an approval in the lineage changes it without touching the copy, so the list's statement works it out from the lineage's current Approved and the copy's base, as the read of a catalog does today.

## What could make a count wrong

A kept count is wrong when a working copy's issues change and neither revision does. The code was read through for that:

- **Every change to a working copy raises its revision.** Every edit of its contents or its rules goes through one method, which raises the revision when the edit changed anything, and renaming goes through it too. Submitting, withdrawing, a rejection, approving, and an update from Approved each raise it in their own statement. A new working copy gets its contents in the transaction that creates it, at revision 0, before it can have a row.
- **Every change of the library that can change an issue raises the library's revision,** in the transaction of the change itself: a feature retired or made active again, a trim or a region deactivated or activated, a global rule added, changed, or deleted. A new name, a new description, a new category, or a new order does not raise it, and validation reads none of those but the names, which go into an issue's words and not into its count. A feature's kind, package or not, cannot change.
- **A release that changes what validation finds** leaves every kept count as the old validation found it, until the copy or the library next changes. Its migration deletes every row of the table, which is one statement that both images run on. What the earlier image keeps in the half minute of that release stands until the next change of the copy or the library.
- **A writer forgotten, or a row never written, costs a whole read and never a wrong count.** That is what parts this from [keeping the issues](0019-every-edit-still-validates-the-whole-catalog-which-is-read-fast-enough-for-it.md), which was weighed and left because a change of the library would have to find the kept issues it makes wrong. Here nothing is found: a row that names another revision is not believed.
- **Nothing wrong is saved or approved by a wrong count.** An edit, a submission, and an approval validate the whole catalog as before, and a wrong count shows in the list alone, until the next change.

## The first ask after a change

It is not spared. After an edit, the next ask of the list reads that one working copy whole and keeps its counts, which by this trace is about 18 ms more on the host than listing it from the row. After a change of the library, the next ask reads whole every working copy whose row names the old revision, which is all twenty at the worst: that ask costs what every ask costs today, once. After working copies are made, the first ask reads each new one whole, which the measurements record as the first ask's own time.

Two ways would spare them, and neither is taken. The answer to an edit could keep the counts, since it validates the whole catalog: that is a write in the path of every save, which the editor sends one after another, for one whole read spared on one ask. A job could validate every working copy of everyone again whenever the library changes, as the worker does for each lineage's current Approved version: that is a job for lists nobody may open, at an admin's rare act, to spare one ask that costs what every ask costs today.

## A deleted working copy, the demo reset, and approval

- **A deleted working copy** takes its row with it, by the reference's `ON DELETE CASCADE`. The statements that delete a working copy table by table stay as they are, which is what lets the image released before the migration, and a reverted one, delete a working copy that has a row. The test that counts the rows of every table with a catalog's column after a delete takes the table in by that column.
- **The demo reset** finds every table that refers to `catalog` by its constraints and empties it, so the table is emptied with the rest at 03:00 UTC. A test holds that.
- **Approval** changes the working copy into an Approved version in the same row, and raises its revision. The kept row outlives the working copy, and approval leaves it there: it names a revision before the approval's, the list reads working copies alone, nothing but the list reads the table, and an id is never given to a second catalog, so the row is never read again. It goes with its catalog, at the demo reset or whenever the version goes. A statement in approval that deletes it would be one line in the approval's transaction, and is not added for a row that harms nothing.

## Considered Options

- **What is the same for every working copy is read once.** The global rules and the names of their features are the same for all twenty, and reading them once would spare two of the three statements of each copy's reading of the library. The trace puts a bound on it: the request's 417.6 ms less all twenty readings of the library, 152.7, is 264.9 ms, and that is more than the 250 the bar asks for before anything is read once. The reading of the library takes 7.1 to 7.6 ms a copy on the host for three statements that bring back a handful of rows, so the time is the statements' round trips, and this way leaves one of the three and all twenty transactions. It would also read the global rules outside the transaction that gives each read one view, so a copy could be counted against rules read a moment before its contents.
- **The twenty are read together,** with one statement for each table. It needs a second way of reading a catalog's contents, holds twenty catalogs in the API's heap at once where the list holds one at a time, with the heap limited to 256 MiB and twenty of the largest catalog there can be never read together, and still validates all twenty. What it would gain cannot be read from the trace, whose steps do not time single statements. And it grows with the catalogs, where a kept count grows with nothing.
- **The cache.** [It keeps the contents of Approved versions](0016-the-contents-of-approved-versions-are-read-from-a-cache-that-is-never-needed.md), which can never be wrong, and a working copy is never in it. A count in the cache would have to be removed at every edit and every change of the library, in the same moment as the database commits, which Redis takes no part in. And a list that leaned on it would be slow again whenever the cache is stopped.
- **The counts kept by the answer to an edit, or made again by a job at each change of the library,** as above.
- **Leaving the list as it is.** Twenty working copies of the demo's largest catalog are listed in a median of 416 ms on the host, and 478 as a browser sees it, each time the dashboard is opened and after each working copy is deleted or withdrawn. For as long as the list is answered, one of the API's threads and one of its ten connections are busy, on a host with two processors. The comment that marks the shortcut names this moment, and this way.

## Consequences

- What the list answers with does not change: the same working copies in the same order, each with its counts as validation finds them against the library as it is today, and whether it is stale. The dashboard page and the browser tests are not changed. An edit still answers with the issues of the whole catalog, validated afresh, and opening a catalog still reads all of it.
- A list of twenty whose counts are all kept sends PostgreSQL a handful of statements where it sends 202: the caller's lookup, the list's own with the kept counts and the library's revision joined to it, and no reading of a catalog. The test that comes with the build holds the exact number. By the trace, such an ask does what the request does once, which was about 27 ms, and the second run on the host has to bear that out: under 250 ms at the median, as the ticket asks, or nothing more is built under it.
- An ask that reads a working copy whole costs one statement more than today, the write of the row, which lies in the trace between one copy's steps and the next's. No step is added for it.
- A working copy has one row, and one person has twenty working copies at the most.
- A migration that changes what validation finds deletes every row of the table.
- The comment at the shortcut, the sentence in `infra/README.md` on what a list of working copies does, and the line of [the record of validating the whole](0019-every-edit-still-validates-the-whole-catalog-which-is-read-fast-enough-for-it.md) that says the list reads and validates each copy are changed with the build, to say what the list does then.
- Still open: a list of twenty of the largest catalog there can be, and many people's lists at once, were not measured, before or after. The measurements say what the run does not show.
